description: Spot-verify the most damning, cheap-to-check claims from review/adversarial sub-agents before relaying them as fact — they can fabricate file/line citations even when the high-level conclusion is correct

  type: feedback

When an adversarial/code-review sub-agent (e.g. the QE-verification workflow) returns concrete `file:line` evidence, treat the citation as a *claim*, not a fact — grep/Read the most damaging, cheapest-to-check ones before presenting them to the user.

**Why:** On the #159 P3 Mode A verification (2026-06-09), an adversarial verifier asserting AC-2 byte-identity was unproven cited a whole test file `lsp-absent-determinism.test.ts` with specific line numbers (192-210, 261-262) and a self-comparison bug `expect(r2.stderr).toBe(r2.stderr)`. A 2-command grep showed **the file does not exist and the bug string is nowhere in `test/`** — fabricated. Yet the agent's *conclusion* was independently TRUE (both real snapshot helpers omit the `step` field and use a `source ?? 'heuristic'` tautology; AC-7's `(j)` block literally self-disclaims "NOT a Mode A reconciliation test"). Conclusion right, evidence partly invented. Relaying the fabricated citation verbatim would have destroyed credibility on a HIGH-risk gate.

**How to apply:** After any review/verify fan-out, before writing the report: pick the handful of blocker-class findings whose evidence is a specific file/line/string and confirm them yourself with grep/Read (cost: seconds). Keep the ones that hold; for the ones that don't, either re-derive the real evidence or drop the finding. Separate "the conclusion survives on verified evidence" from "this specific citation was wrong." This is the review-output analogue of [[feedback-verify-pre-existing-claims]] (don't trust a claim — run/grep it) applied to sub-agent output rather than to "pre-existing failure" excuses.

**Sharpening — findings that recommend WEAKENING a guard are the highest-risk class (verify against RUNNING code, not design prose):** On #166 (2026-06-10) an adversarial design finding claimed `mode-a-golden.test.ts:370`/`:486` hard `expect(r.source).toBe('heuristic')` "contradict the B1 non-goal" and should coalesce to `r.source ?? 'heuristic'`. It conflated "RED pre-fix on an in-progress branch" with "wrong assertion." On the actual code every CALLS emit stamps `source:'heuristic'` in-memory, so the hard equality is a load-bearing B1 contract and the suggested `?? 'heuristic'` would have created a tautology that masks a missing-stamp regression. The bad finding propagated into the plan AC, the design KD-5, AND the issue body before an engineering-team investigation caught it — because everyone trusted the design prose over the on-disk test. Rule: any finding that says "loosen / coalesce / delete this assertion" gets re-verified against the running test + the code it guards before it touches a plan. See [[project-p3-mode-a-inert-on-active-path]].
