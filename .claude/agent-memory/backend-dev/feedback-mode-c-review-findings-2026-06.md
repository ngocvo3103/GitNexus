On 2026-06-12, the Mode C measurement-campaign harness (`gitnexus/scripts/measure-mode-c.ts` + `docs/designs/159-mode-c-measurement.md`) was reviewed for a second time and produced six BLOCKER/MAJOR findings. The reconciliation path was: **re-scope the design doc to LSP-at-verify (NOT ship per-leg analyze)**, plus the per-finding fixes below. This overwrites the prior "per-leg analyze won" reconciliation in the earlier version of this memory — that path was a misinterpretation; the actual shipped harness reuses the same heuristic-only index for both legs.

**Why:** The 2026-06-12 review explicitly named two BLOCKERs that were in direct contradiction: the design doc's EdgeCase "Per-leg analyze flag (resolved — was a follow-up, now shipped)" claimed the harness re-runs `analyze --lsp` for the `lsp` leg, but the harness comment at `measure-mode-c.ts:475-486` explicitly said "True pre/post index comparison (a distinct LSP-augmented index) requires per-leg `analyze --lsp` support — a follow-up WI, NOT this slice." The test at `test/unit/scripts/measure-mode-c.test.ts:436-437` pinned "The single call has NO `--lsp` flag (KD-3: same index)." The doc and the code disagreed; the test pinned the code. Resolving by re-scoping the design doc to "LSP-at-verify delta on the heuristic index" is honest about what shipped and keeps the tests as the source of truth.

**How to apply:** For future campaign harnesses (any "compare two leg variants of an index" pattern):
- When implementation and spec disagree, the side with tests wins. Update the losing side's docs to match. Do NOT "fix" the implementation to match a spec claim that wasn't tested.
- KD-5/I-6 forbids single-rate cherry-picking: the headline table publishes ONLY the (reported, conditional, refusal) triple — never precision/recall alongside it. Drop the columns; full `VerifyReport` precision/recall remain available in the per-leg JSON artifacts.
- The source-distribution query against `CodeRelation` MUST be relationship-agnostic (no `WHERE r.type = $relType`). A CALLS-only filter silently narrows the campaign to one edge type when IMPORTS/IMPLEMENTS/EXTENDS/HAS_METHOD edges are present in the schema and may be affected by Mode A.
- The plan's §Summary, §Implementation Plan, and individual WI sections must mirror the design's narrower claim. A reader of the plan alone should not be misled into expecting per-leg indexes when the design + code + tests all pin the same-index LSP-at-verify model. Add a "NOT SHIPPED — filed as follow-up WI" callout to every place the plan still references the stronger claim.
- Pre-#170 baseline SHA MUST be enforced at the CLI level, not just documented. The `--expected-before-sha` flag + `FlowFateHaltError` code 4 on mismatch is the mechanical enforcement; without it a campaign operator can silently point `--before` at the wrong commit and the verdict reflects the wrong baseline.
- Entry-point candidates are derived via a separate cypher query (the `Process` table does not persist the entry-point score). The shipped query is `MATCH (p:Process) WHERE p.entryPointId IS NOT NULL RETURN DISTINCT p.entryPointId` — the set of distinct entry-point ids used across all processes is the best proxy for the production `calculateEntryPointScore > 0` set. An all-zero count in production is a contract violation; a cypher throw is "no candidate info available" (legacy index).
- LSP pre-measure gate has a 3-step fallback: (1) `--lsp-server-path` (operator-pinned, bypasses discovery), (2) `discoverServers` PATH lookup, (3) `npx -p typescript-language-server --version` one-shot probe. The third step is the "installed but not on $PATH" recovery that the prior gate missed; doctor message lists the same three remediation paths in the same order.
- The harness's per-repo gate MUST capture the `stat` result once and reuse it; the prior code called `stat` twice on the cache-present path (the second call walked `.gitnexus/lbug` recursively to populate `dbSizeBytes`). Factor a `readSharedState` helper that consolidates the duplicated `loadMeta` + two `bucketEdgeCounts` cypher queries — both the cache-present and post-`analyze` paths call the same helper.
- The Excluded-section renderer must distinguish three failure modes (lsp-unavailable / under-sampled / harness-error) and APPEND "also under-sampled" to the harness-error reason when a verifier throw also implies the leg was under-sampled. The prior priority chain collapsed them, silently violating I-5's "partial metrics never silently published" intent.
- `underSampled:true` is overloaded across three distinct failure modes: (a) `lspUnavailable` (verifier short-circuit), (b) `sampledCap < sampleSize` (caller-runnable cap), (c) harness/verifier error. The Excluded section must distinguish them; the harness prefixes per-leg errors with `harness-error:` and forwards `lspUnavailable.reason` verbatim.
- The `noRecallRegression` verdict attaches a `lowBaselinePower:true` flag when `baseline.recallMisses === 0` (the misses clause is trivially satisfied and the verdict reduces to a coverage check). The renderer surfaces the flag in its own column so downstream consumers can spot trivially-passing verdicts.
- `VerifyFn = (opts: any) => Promise<any>` is fragile — type the seam as `(opts: RunModeCVerifyOpts) => Promise<VerifyReport>` (structural mirror) so a field-rename in the production interface fails the harness's static typecheck, not silently at runtime.
- The harness hoists repo-level reads (`loadMeta`, two `bucketEdgeCounts` cypher queries, `stat`) OUT of the per-leg loop and caches them in shared variables. Perf: 2 legs on a 1000-edge run = 50% fewer cypher queries + stat walks.
